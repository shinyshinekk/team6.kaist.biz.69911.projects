## 1. 나의 관점

‘뚜’의 경쟁력은 기혼자라는 타이틀만으로 만들어지지 않는다. 주선자가 자기 지인의 소개를 계속 도울 수 있어야 하고, 소개받는 싱글이 수동적으로 기다리지 않고 관심을 표현할 수 있어야 한다. 다만 소개를 강제하거나 정보를 넓게 공개해서는 안 된다. 나는 **신뢰하는 사람의 도움과 당사자의 선택을 결합해, 실제로 이어질 소개 기회를 늘리는 일**이 핵심이라고 본다.

## 4. 부가 관계·Why Up / How Down에서 새로 찾은 것

- **보조 관계(점선 화살표)**: S5 → W32. 싱글의 스타일 요청은 본래 싱글의 선택권을 돕지만, 주선자의 다음 행동을 알려주는 신호도 된다. 둘 중 **주목적은 W22**로 둔다.
- **새로운 대안(H1, 점선 상자)**: 주선자의 요청 수신량 조절. 주선자에게 요청이 몰리면 '누구든 보낼 수 있다'는 구조가 오히려 참여를 위축시킬 수 있다는 위험을 고려한 가설이다. **현재 PRD의 확정 기능이 아니며 이번 HW6 개인 구현 범위에는 넣지 않는다.**
- 기존 팀 WhyTree가 아니라 2026-10-27 최신 PRD의 **기혼 주선자 중심·복수 연결·싱글 능동 요청**을 개인 관점에서 다시 목적-수단으로 묶었다.

## 5. 선택 기능: S5 / F18

**선택: F18 '원하는 스타일 알려주기 → 내가 승인한 주선자 한 명에게 요청 → 주선자 검토·종료'.**

왜 이 기능인가:
1. S5에서 W22(싱글 주도권)까지 Why가 명확하고, 주선자 다음 행동(W32)까지 연결된다.
2. PRD의 SLC 순간(싱글 관심 신호가 주선자 행동으로 전환)과 11/7 P0-Beta에 직접 기여한다.
3. 구체적인 의사결정이 아직 남아 있으므로 `/grill-me`에 적합하다: 요청 필드, 수신자 권한, 중복, 철회, 처리 상태, 거절 이유/알림 등.
4. 하나의 요청·검토 루프를 개인 폴더에서 모의 데이터로 시험할 수 있고, 팀의 핵심 인증/DB를 건드리지 않는다.

**보호 원칙(이미 PRD에 있는 확정·선택 방향)**
- 하나의 넛지는 **싱글이 선택한 승인 주선자 1명에게만** 간다. 다른 주선자·다른 싱글에게 자동 전송하지 않는다.
- 관심/스타일 요청은 소개 제안·상대방 수락·연락처 공개·실제 만남을 **대체하지 않는다**.
- 공개 설정이 L0여도 스타일 요청은 가능하며, 프로필 공개 동의와 넛지 요청 동의는 구분한다.
- 운영자는 기본적으로 중앙 매칭을 하지 않는다.
- 개인 시연에서 가상 인물만 사용한다. 실제 서버의 역할 기반 권한 통제는 별도 통합·보안 검증 대상이다.

## 6. 아직 본인이 결정할 문제 (/grill-me)

1. 싱글이 무엇을 입력해야 요청 품질은 확보하면서 부담을 줄일까? 선택 태그/자유 서술/둘 다?
2. 한 명의 싱글이 동일 주선자에게 요청을 어느 정도의 빈도로 보낼 수 있나?
3. 수신 주선자가 바쁘면 `보류` 상태를 둘 것인가? `검토/종료`만으로 충분한가?
4. 싱글이 요청을 철회·수정하면 이미 열린 주선자 화면은 어떻게 바뀌어야 하나?
5. 주선자가 요청을 거절할 때 이유가 필요할까? 싱글에게 얼마나 알릴까?
6. 공개 수준 L0/L1/L2 및 다른 주선자 관계 정보를 수신함에서 어떻게 감출까?
