# TTU — 한 건을 끝내는 소개 보드

v1.1 / 2026-10-28 / 사용자 문제 선택·자율 작성 위임에 따른 명세.

변경 기록: v1.1은 화면 검증에서 발견한 다음 행동 안내의 어색한 조사를 명시적인 문장으로 고친다. WhyTree 미리보기는 CSP에 맞는 별도 CSS를 쓰고, 함께 제공하는 PPTX/PDF를 명시적 파일 목록으로만 읽을 수 있게 한다. 단계·동의·집계 규칙은 v1.0을 유지한다. 이 변경을 먼저 기록한 뒤 코드에 반영한다.

## 누구의 어떤 문제인가

기혼 주선자가 여러 소개를 함께 진행할 때 누구의 확인을 기다리는지, 지금 무엇을 해야 하는지, 실제로 연결이 끝났는지를 기억하고 메신저를 뒤지는 수고가 크다. 한 화면에서 단계와 다음 행동 한 가지를 보여주고, 단계별 독립 응답에 따라 진행을 기록한다. 후보를 자동으로 찾아주거나 관계 성사를 보장하는 기능은 아니다.

WhyTree: `좋은 소개를 끝까지 이어주기 > 주선자의 조율 부담 줄이기 > 소개 진행 상태 한곳에 모으기`. 다른 두 가지인 선택권과 실제 연결 확인은 보드의 상태 규칙에 반영한다.

## 정한 작은 범위와 전제

이미 서로 협력하고 후보의 최소 요약을 공유할 동의를 받은 주선자 A/B와 합성 후보 코드만 사용한다. 실제 회원 가입·관계 승인·협력 링크·프로필 데이터는 이번 개인 기능 밖이다. 테스트 actor 선택은 실제 인증이 아니다. 서버는 해당 합성 actor의 참여 관계·역할·현재 단계를 검사하지만 실서비스 신원 인증·기혼 검증을 했다고 주장하지 않는다. 실명·사진·연락처·자유 메모 입력 필드를 두지 않는다.

## 사용 순서

1. 주선자 A로 보드를 연다. 자신의 소개 건만 단계/다음 행동과 함께 보인다. 모든 숫자와 기록은 합성 데모다.
2. 승인된 합성 후보 쌍으로 소개 건을 하나 만든다. 같은 쌍의 진행 중 소개를 중복 만들 수 없다.
3. 참여 주선자 A/B가 각자 검토한다. 양쪽 검토 뒤에만 싱글 소개 동의 단계로 간다.
4. 합성 싱글 역할에서 각각 소개 수락/거절을 기록한다. 양쪽 수락 후에도 정보 공유 승인은 별도다. 주선자가 싱글 응답을 대신 클릭할 수 없다.
5. 싱글 양쪽이 각각 공유를 승인해야 연결 확인 단계가 열린다. 연락은 발송하지 않는다. 두 주선자가 각자 합성 시나리오의 실제 연결 확인을 기록한 뒤에만 소개 완료로 센다.
6. 소개 완료 후 만남 확인/아직 만나지 않음/미확인을 기록해 후속 상태를 남긴다. 소개 연결과 실제 만남은 서로 다른 기록이다.
7. 보류는 진행을 멈추며 기존 기록을 지우지 않는다. 참여자 철회·거절은 소개를 종료한다. 공유 화면에는 누가 거절했는지나 이유를 노출하지 않는다. 종료 뒤 진행 버튼은 작동하지 않는다.
8. 새로고침/서버 재시작 뒤에도 로컬 데이터가 남는다. 데모 초기화는 합성 초기 기록으로 돌린다.

## 상태와 다음 행동

보드 상태는 기록에서 계산한다. 주선자 검토 → 싱글 소개 동의 → 별도 정보 공유 동의 → 양쪽 주선자 연결 확인 → 후속 확인/정리. 보류·종료가 진행보다 우선한다. 한쪽 수락, 공유 승인, 주선자 연결 확인만으로 소개 완료를 만들지 않는다. 다음 행동은 현재 actor가 할 수 있는 행동 또는 기다리는 절차를 한 문장으로 표시한다. 오래 기다렸다는 이유로 자동 승인·성사·재촉 알림을 만들지 않는다.

## 우선순위와 제외 범위

| 우선순위 | 항목 | 완료 기준 |
|---|---|---|
| P0 | 내 소개 보드·필터·다음 행동 | 참여한 소개만 보임. 검토/동의·연결·후속 단계 및 보류/종료 구분 |
| P0 | 합성 소개 생성·단계 전이 | 역할별 독립 응답, 동일 진행 쌍 중복 차단, 모든 선행 조건 검사 |
| P0 | 소개/공유 동의·철회 | 주선자 대리 응답 금지. 공유 승인은 수락 뒤 별도. 종료 시 거절자·이유 비공개 |
| P0 | 연결·후속 확인 | 주선자 양쪽 확인 후만 introduced. 후속 만남 상태는 별도 |
| P0 | 저장·오류·동시 변경 | 서버 atomic JSON 저장. 실패 시 상태 미반영, 오래된 version은 409. 중복 요청은 한 번만 처리 |
| P0 | 합성 데모·관계 검사 | M-C의 타 건 조회/변경 차단. 실제 인증과의 한계를 화면에 명시 |
| P1 | 원격 실제 계정·기존 TTU 앱 통합 | 별도 인증/관계/보안 설계 후 |
| P1 | 일정 조율·알림 설정·검색 | 직접 소개 흐름 확인 뒤 |
| P2 | AI 후보 추천·전역 탐색·리워드·채팅 | 이번 과제 미구현 |

실행 중 AI 모델과 외부 API는 사용하지 않는다. 규칙 기반 다음 행동은 모델 장애가 없다. 오류 시 기존 상태를 유지하고 실패를 설명하며 다시 읽게 한다. 실제 서버/연락 서비스 장애의 운영 대응을 구현했다고 주장하지 않는다.

## 손으로 하는 체크 3개

1. **정상 한 바퀴:** 합성 소개 생성 → 주선자 A/B 각각 검토 → 싱글 둘 각각 수락 → 각자 별도 공유 승인 → 주선자 A/B 각각 연결 확인 → 후속 상태 기록. 중간 한 명만 응답했을 때 다음 단계/완료가 열리지 않는지 확인한다.
2. **경계/비공개:** 무관한 M-C는 건을 볼 수 없다. 주선자 역할로 싱글 동의를 바꿀 수 없다. 참여 싱글이 거절/철회하면 종료되고 공유 보드에 거절자·이유가 표시되지 않는다. 보류·종료 후 진행이 막히는지 본다.
3. **지속/실패:** 새로고침·서버 재시작 후 기록 유지, 중복 버튼/오래된 version 요청이 상태를 두 번 올리지 않는지, 저장 실패가 성공으로 보이지 않는지 확인한다. 마지막에 합성 데모를 초기화한다.

agent 자동/화면 검사와 사용자 본인 검사는 별도다. 실제 본인이 위 체크를 했다고 미리 쓰지 않는다.

## 설계 검토 성격

실제 사용자 발언은 제품 TTU, 최신 주선자 문제, 추가 세부 질문 대신 자율 작성 위임이다. 이 명세의 상태·범위·예외 처리는 위임 아래 내린 설계다. Matt Pocock grill-me/grilling의 질문 구조로 선택지를 검토했으나 실제로 하지 않은 라운드/사용자 답변을 기록하지 않는다. 엄격한 대화형 면담 요건과 본인 수동 검사 확인은 최종 체크리스트에 남긴다.
