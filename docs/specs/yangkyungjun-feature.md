## 0. 이 문서가 결정하는 것

PRD v0.5 는 1.3 말미에 **"세부 넛지 한도는 미결정"**이라고 적고 칸을 비워 두었다. 이 스펙이 그 칸을 채운다.

## 1. 한 문장

**싱글이 자신과 연결된 기혼 주선자 한 명을 골라, 양보할 수 없는 조건 2개와 양보 가능한 조건을 담아 "이런 사람 소개해 주세요"를 보내고, 주선자는 받은 부탁함에서 확인·보류·종료한다.**

### 왜 이 기능인가 (WhyTree 경로)

①은 WhyTree 에서 **두 갈래에 동시에 매달려 있다.**

```
지인의 좋은 인연을 더 많이
├─ ★ 소개 경로 확장
│   └─ 내 지인 안에서 찾기
│       └─ ① 소개 부탁 보내기        ← 주선자가 움직일 계기를 만든다
└─ 소개 품질 개선
    └─ 필수·양보 조건 전달
        └─ ① 소개 부탁 보내기        ← 조건을 구조화해 전달한다
```

그래서 ①은 ★ 차별화(2촌 릴레이) 자체는 아니지만, **그 위에 올라탈 입력 노드**다.
P1(이상형 반전 테스트)과 P2(2촌 릴레이)는 둘 다 **"부탁 객체"가 먼저 고정되어야** 얹을 수 있다.

### 경계 — 이 기능이 끝나는 곳

- **UI 책임은 주선자가 `확인`을 누르는 순간까지.** 그 뒤 실제로 지인을 고르고 소개장을 쓰는 일은 **②(받은 소개 부탁함 → 소개 제안)**의 몫이다.
- **데이터 책임은 부탁이 닫힐 때까지.** 부탁을 끝내는 규칙이 부탁 객체 바깥에 있으면 그건 확정된 스키마가 아니다. 그래서 `확인` 이후에도 만료 시계는 계속 돈다(§3.4).

## 2. 제약 — PRD 가 이미 정한 것

| 출처 | 내용 | ①에 미치는 영향 |
|---|---|---|
| **D13** | 싱글↔주선자 **다대다** 연결 | 부탁의 단위를 `(싱글 1, 주선자 1)` 쌍으로 잡는다. 여러 주선자에게 각각 따로 보낼 수 있다 |
| **D14=A** | 첫 발견 범위 = 내 승인 주선자 후보풀 | 부탁은 **내 연결 주선자에게만** 간다. 2촌 전달은 범위 밖 → **P2** |
| **D17** | 기본 L0·미동의, 공개는 단계 동의 | 부탁에는 **내 조건**만 담기고 **내 프로필은 담기지 않는다**. 주선자는 이미 나를 아는 지인이다 |
| **1.3** | 주선자가 **Primary** 고객 / 최대 리스크 = 주선자 지속 활동 | 충돌 시 **주선자 부담 감소**가 싱글 편의보다 우선한다 |
| **1.2** | "소개가 흐지부지되면 피드백이 없다" | **만료**를 상태로 만든다(§3.4) |
| **H6** | 싱글의 능동적 관심 표현 선호 · **압박 여부 기록** | 한도·쿨다운이 전부 여기서 나온다 |
| **3절** | AI 는 **11/7 범위 제외** | 이상형 반전 테스트 → **P1** |

## 3. 설계

### 3.1 조건 — 필수 vs 양보를 무엇으로 표현하는가

**항목 7개에 등급 하나씩**을 매긴다. 자유 텍스트 두 칸이 아니다.

| 항목 | 값 |
|---|---|
| 나이대 | 20대 중후반 / 30대 초반 / 30대 중후반 / 40대 이상 |
| 거주 지역 | 서울 / 경기·인천 / 대전·세종 / 부산·경남 / 그 외 지역 |
| 결혼 의향 시점 | 1년 안에 / 2~3년 안에 / 아직 정하지 않음 |
| 종교 | 무교 / 기독교 / 천주교 / 불교 |
| 흡연 | 비흡연이었으면 / 흡연해도 괜찮음 |
| 직업·학력 성향 | 전문직·연구직 / 사무·기업 / 자영업·창업 / 직업보다 태도 |
| 성격 | 외향적인 편 / 내향적인 편 / 상황에 맞춰 유연한 편 |

등급: **`must`(필수) · `prefer`(선호) · `any`(상관없음)** — 여기에 **자유 한마디 1칸(200자, 선택)**.

> **왜 자유 텍스트 2칸이 아닌가.**
> 칸을 "원하는 조건 / 양보 가능한 조건" 두 개로 주면 사람들은 양쪽에 비슷한 걸 적거나 양보 칸을 비운다.
> **양보는 적어내는 것이 아니라 포기를 강요당할 때만 드러난다.** 그 강요 장치가 아래 필수 상한이다.

#### ★ 핵심 규칙: 필수는 최대 2개

```
필수(must) ≤ 2   그리고   필수 + 선호 ≥ 1
```

상한이 없으면 모두가 전 항목을 "필수"로 찍고, 그 순간 주선자가 받는 것은 소개 부탁이 아니라 **불가능 조건표**다.
상한이 있으면 사용자는 **무엇을 포기할지 직접 고르게 되고**, 그 선택 자체가 "양보 가능한 조건"이 된다.

> **이것이 H6 의 "양질 요청" 정의다:** `필수 ≤ 2 ∧ (필수+선호) ≥ 1`.
> PRD 가 숫자만 있고 정의가 없던 판정 기준을, 기계가 셀 수 있는 명제로 바꾼다.

**부수 효과:** 주선자의 부탁함 카드에는 **필수 2개만 먼저** 보인다. 지인을 떠올릴 때 거를 기준이 둘뿐이면 판단이 빠르다 → PRD 최대 리스크(주선자 이탈)에 직접 듣는다.

### 3.2 부탁의 단위와 한도

부탁 1건 = **싱글 1명이 주선자 1명에게 보낸 것**. 한 부탁이 여러 주선자에게 동시에 뿌려지지 않는다.

> **왜 브로드캐스트가 아닌가.** 한 부탁을 여러 주선자가 같이 보면 중복 노동이 생기고 "남이 하겠지"로 아무도 안 움직인다.
> PRD 1.3 이 주선자를 Primary 로 두고 최대 리스크를 "주선자 지속 활동"으로 잡은 이상, 이 구조는 쓸 수 없다.
>
> **왜 평생 1명이 아닌가.** D13 이 다대다를 확정했고 H7 이 "복수 연결이 기회를 넓히는가"를 검증 가설로 세웠다.
> 부탁을 한 명에게만 묶으면 H7 을 측정할 데이터 자체가 쌓이지 않는다.

| 값 | 결정 | 근거 |
|---|---|---|
| 동시 진행 부탁 | **3건** | PRD "넛지 한도 미결정" 칸을 채운다 |
| 같은 주선자 중복 | **진행 중이면 금지** | 같은 사람에게 두 건이 떠 있을 이유가 없다 |
| 같은 주선자 누적 | **30일 내 2건** | 취소→재전송 반복 스팸 차단(§3.5) |

### 3.3 상태

| 내부 상태 | 싱글에게 보이는 라벨 | 나가는 전이 |
|---|---|---|
| `sent` | 전달됨 | 확인 · 보류 · 종료 · 만료 · 취소 · (열람 전)수정 |
| `held` (보류) | **전달됨** | 확인 · 종료 · 만료 · 취소 |
| `accepted` (확인) | 찾아보는 중 | 종료 · 만료 · 취소 |
| `closed` | 이번엔 닫힘 | — (종착) |

`closedReason`: `declined` · `expired` · `cancelled` — **내부에만 저장한다.**

```
            ┌──── 취소(싱글) ────────────────────────┐
            │                                        ▼
  [sent] ──확인──▶ [accepted] ──종료──▶          [closed]
     │  │                │                           ▲
     │  └──보류──▶ [held] ┴──종료──▶ ─────────────────┤
     │                 │  └──확인──▶ [accepted]       │
     └──종료──────────────────────────────────────────┤
                                                      │
     ····· 만료(시계) ·································┘
```

#### 싱글에게 세 가지만 보이는 이유

- **`종료`와 `만료`가 같은 문구인 이유.** 내가 거절했다는 사실이 지인에게 그대로 전달되면, 주선자는 종료 버튼을 안 누르고 그냥 앱을 닫는다. 그러면 모든 부탁이 만료로만 흘러가고 §3.4 가 만들려던 데이터가 죽는다. **두 문구가 같아야 종료 버튼이 살아난다.** 이것은 UI 장식이 아니라 데이터 품질 장치다.
- **`보류`를 노출하지 않는 이유.** "보류"는 싱글에게 *밀리고 있는 중*으로 읽힌다. 보류는 주선자가 자기 부탁함을 정리하고 기한을 미루는 도구이지, 싱글에게 보낼 신호가 아니다.
- **`확인`은 노출하는 이유.** `찾아보는 중`이 싱글에게 가는 유일한 희망 신호다. 이것마저 없으면 PRD 1.2 의 "주선자가 움직일 때까지 대기만 하면 효용이 낮다"에 그대로 걸린다.
- **프라이버시 비대칭 보정.** D17 은 싱글의 정보를 L0 기본·단계 동의로 촘촘히 보호하는데, 주선자의 **거절 의사**에는 아무 보호가 없었다. 주선자가 Primary 인 이상 이쪽 보호가 더 급하다.

### 3.4 시계 — 흐지부지를 상태로 만든다

PRD 1.2 가 지목한 문제는 **"소개가 흐지부지되면 피드백이 없다"**이다. 흐지부지 = 아무 버튼도 안 눌린 상태다.
버튼만 있는 모델에는 그 상태가 없다. 그래서 **시계를 넣는다.**

| 값 | 결정 |
|---|---|
| 만료 | **7일** |
| 보류 연장 | **+7일, 1회만** |
| 확인 연장 | **+7일** |

- **만료가 없으면 한도 3건이 영구히 잠긴다.** 무응답 건이 `sent` 에 영원히 머물면 싱글은 3건을 쓴 뒤 아무것도 못 한다. **한도와 만료는 한 쌍이라 따로 결정할 수 없다.**
- **`확인` 뒤에도 시계가 도는 이유.** "일단 찾아볼게"는 한국어에서 가장 정중한 기본 응답이고, 따라서 가장 자주 밟히는 경로다. 여기서 시계를 멈추면 **가장 흔한 경로가 슬롯을 영구히 잠근다.**
- **만료는 주선자에게 면죄부다.** 거절 버튼을 누르는 것 자체가 부담이라 주선자는 그냥 앱을 안 연다. 시계가 대신 닫아주면 주선자는 죄책감 없이 넘어가고 싱글은 최소한 **끝났다는 사실**을 안다. (WhyTree "조용히 끝나는 부탁" / "바쁠 땐 알림 쉬기"가 가리키던 것)
- **왜 72시간이 아닌가.** H4 의 72시간은 싱글이 소개 제안에 답하는 속도다. 주선자가 지인을 떠올리는 일은 몇 주짜리다. 72시간을 들이대면 전부 만료로 끝난다.
- **왜 14일이 아니라 7일인가.** 베타가 11/7~12/19 로 6주뿐이다. 14+14 면 한 건이 최장 28일을 먹어 베타 안에 "닫힘"이 거의 안 쌓인다. **숫자는 나중에 늘릴 수 있지만 안 쌓인 데이터는 되돌릴 수 없다.**

### 3.5 싱글의 권한 — 취소와 수정

WhyTree 의 "내 정보 통제 ↑ / 공개 범위 3단계·**철회**"에 대응한다. 부탁에는 내 조건이 담겨 있는데 철회 수단이 없으면 안 된다.

| 액션 | 조건 |
|---|---|
| **취소** | 언제든. 한도 즉시 반환. **쿨다운 면제** |
| **수정** | **주선자가 아직 열어보기 전(`readAt == null`)**까지만 |

- **수정에 열람 경계를 두는 이유.** 수정 수요는 사실상 전부 "보낸 직후 오타·실수"이고, 그 구간은 주선자가 아직 안 열어본 구간과 거의 정확히 겹친다. **열람 이후의 수정은 주선자가 이미 머릿속으로 지인을 훑어본 수고를 통째로 버린다.**
- **취소에 쿨다운을 걸지 않는 이유.** 쿨다운은 "주선자가 닫은 걸 다시 들이미는 압박"(H6)을 막는 장치다. 내가 스스로 닫은 건 그 대상이 아니다.
- **대신 누적 상한을 둔다.** 쿨다운을 면제하면 취소→재전송을 무한 반복할 수 있으므로 `같은 주선자 30일 내 2건`으로 막는다.

### 3.6 쿨다운

| 값 | 결정 |
|---|---|
| `declined` / `expired` 이후 같은 주선자 재부탁 | **14일** |
| `cancelled` 이후 | **면제** |

`expired` 에도 쿨다운을 거는 이유: 무응답은 대체로 **말 없는 거절**이다. 7일 침묵한 사람에게 8일째 다시 보내는 것이 H6 가 기록하려는 "압박"의 전형이다.

### 3.7 스키마

```js
IntroRequest {
  id:              string
  singleId:        string
  matchmakerId:    string          // D13: 쌍마다 1건
  conditions: {                     // 7개 항목 전부 존재
    [fieldKey]: { grade: 'must' | 'prefer' | 'any', value: string | null }
  }
  note:            string           // ≤ 200자, 선택
  state:           'sent' | 'held' | 'accepted' | 'closed'
  closedReason:    'declined' | 'expired' | 'cancelled' | null
  createdAt:       number
  updatedAt:       number
  readAt:          number | null    // 상태가 아니라 타임스탬프. 수정 권한의 경계
  expiresAt:       number           // 확인/보류 시 갱신
  closedAt:        number | null
  holdExtensions:  number           // ≤ 1
}
```

**불변식**

1. `conditions` 에서 `grade === 'must'` 인 항목 수 ≤ 2
2. `grade !== 'any'` 인 항목 수 ≥ 1, 그리고 그 항목들은 `value !== null`
3. 한 `(singleId, matchmakerId)` 쌍에 `state !== 'closed'` 인 건은 최대 1개
4. 한 `singleId` 에 `state !== 'closed'` 인 건은 최대 3개
5. `state === 'closed'` ⟺ `closedReason !== null` ⟺ `closedAt !== null`
6. `state !== 'closed'` 이면 언제나 `expiresAt > closedAt 없음` 이며, `now >= expiresAt` 인 순간 `expired` 로 닫힌다
7. `holdExtensions <= 1`

**시간은 반드시 주입한다.** 모든 함수가 `now` 를 인자로 받고 내부에서 `Date.now()` 를 부르지 않는다. 만료·쿨다운이 전부 시간 기반이라, 시계를 주입하지 않으면 검증 자체가 불가능하다.

**P1 이 스키마를 바꾸지 않는다는 점이 중요하다.** 이상형 반전 테스트의 출력은 결국 "어느 항목이 필수인가"의 등급 배정이다. §3.1 구조에서 반전 테스트는 **같은 필드를 채우는 또 하나의 입력 경로**일 뿐이고, AI 가 실패하면 수동 입력으로 떨어진다(WhyTree "AI 실패 시 고정 질문"). 조건을 자유 텍스트로 받았다면 P1 은 텍스트 파싱부터 해야 했다.

**P2 도 마찬가지다.** 부탁 단위가 `(싱글, 주선자)` 쌍이므로, 2촌 릴레이는 **같은 조건을 담은 새 부탁을 2촌 주선자 앞으로 만드는 일**이 된다. 원본 부탁에 `relayedFrom` 한 필드만 붙으면 된다.

## 7. 측정 — 이 기능이 PRD 가설에 돌려주는 것

| PRD 가설 | 이 기능이 내놓는 수치 |
|---|---|
| **H6** 싱글이 능동적 관심 표현을 선호하는가 | 전송 건수 / **양질 요청**(`필수 ≤2 ∧ 선호 ≥1`) 비율 / 거부된 전송의 사유별 분포 |
| **H6** 압박 여부 | `COOLDOWN_ACTIVE`·`MATCHMAKER_WINDOW_LIMIT` 로 막힌 시도 수 = 더 보내고 싶었던 횟수 |
| **H1 / H3** 주선자가 자발적·반복적으로 움직이는가 | `declined` 대 `expired` 비율. **만료가 많으면 주선자가 앱을 안 연 것**이고, 종료가 많으면 최소한 반응은 한 것이다 |

| **1.2** 흐지부지 문제 | 전체 부탁 중 `expired` 비율 |

**분자/분모를 함께 기록한다**(PRD 2.2 지침). 표본이 작아 비율만으로는 아무 말도 할 수 없다.
